# publish-post

You convert the author's draft into a finished post and prepare a PR. The author supplies ideas and substance; you supply structure, SEO, assets, checks and the PR. The site publishes queued posts on a schedule (see `publishing/config.json`), so a merged post is **queued**, not live.

Work from the main checkout of this repo (`/Users/dinesh/Documents/dg-journal/my-journal`). Read these first: `.claude/skills/publish-post/style.md`, `publishing/config.json`, `blog/tags.yml`, and run `npm run -s queue`.

## Hard rules

1. **The draft is the source of truth.** Restructure, tighten, explain, add transitions, an intro and a summary. **Never add facts, numbers, prices, versions, benchmarks, quotes, or claims about a product that the draft or its `sources:` does not contain.** If something needs support, keep the author's wording and add it to the PR's "Verify before merge" list.
2. Keep the author's voice and opinions. Do not soften or hype.
3. No mention of AI assistance anywhere in the post or its footer (author's decision).
4. Stop and tell the author if the draft contains secrets, tokens, private customer data, or text copied from a source that looks unlicensed.
5. Never push to `main`, never merge. The only outputs are a branch and a PR (plus one PR in the code repo when needed).
6. Queued posts must have `draft: true`, an explicit `slug`, an `image`, and pass `npm run lint:content`.

## Procedure

**0. Preconditions.** `gh auth status` works; `git fetch origin`; main checkout has no uncommitted tracked changes. With no argument, list `drafts/inbox/*.md` and process each in turn (one PR per draft).

**1. Read the draft.** Optional frontmatter hints: `type` (essay | guide | field-notes | reference | quick-take | auto), `series`, `title`, `publish_on`, `code` (files to publish), `sources` (URLs). Everything else is body.

**2. Classify.** Pick one `post_type` and use its template in `.claude/skills/publish-post/templates/` (read `templates/README.md` first):
- `essay` (blog): a concept or design philosophy. `guide` (docs series): reproducible step-by-step build. `field-notes` (blog): lessons from building/running something. `reference` (blog or docs hub): a map of a topic, kept updated. `quick-take` (blog): a short reaction or single idea.
- Say your call and why in one line. Ask the author only when it is genuinely ambiguous, or a guide needs a series name you cannot infer. Prefer an existing series; otherwise create one: `docs/<series>/_category_.json` with `label`, `position`, and `link: {type: generated-index, slug: /<series>, title, description}` (the sidebar is autogenerated).
- **Evidence gate:** the post needs at least one first-hand artifact from the author (a real number, a prompt/output they ran, a failure, a screenshot). If the draft has none, ask for one before writing. Never invent one; if there truly is none, say so in "Verify before merge" and keep the post short and framed as opinion.
- **Search intent:** write down the one query this post should answer (for example "context engineering vs prompt engineering"). The title, first paragraph and one H2 should match it. Put it in the PR body.

**3. Name it.** `slug`: kebab-case, keyword first, <= 60 chars, never changes after release. Filename `YYYY-MM-DD-<slug>.md` using today's date.

**4. Isolate.** `scripts/publish/start-post.sh <slug>` creates a worktree at `../my-journal-posts/<slug>` on branch `post/<slug>`. Do all edits there.

**5. Write the content** from the chosen template and `style.md` (every long post has a `:::tip TL;DR` box, a hook with tension, a limits section, **Key takeaways**, a Discuss line and Related reading). Frontmatter for a queued post:
```yaml
---
slug: <slug>
title: "<<= 60 chars, specific promise, keyword first>"
image: /img/social/<slug>.png
date: <today>
draft: true
post_type: <essay|guide|field-notes|reference|quick-take>
publish_order: <next integer after the highest in the queue>
authors:
  - dgopal
tags: [<=5, reuse keys from blog/tags.yml>]
description: "<120-160 chars: what the reader will learn>"
---
```
(Guides: same minus `authors`; add `sidebar_label` only if the title is long.) Delete all template guidance comments. Add 2-4 links to related existing posts/guides (look them up; use root-relative paths or the relative `.md` file link style already used in the repo). Add the series "previous/next" links when the post belongs to a series.

**6. Tags.** Reuse existing keys exactly as written in `blog/tags.yml`. For a new tag, append an entry (key = label, `permalink`, one-line `description`). `lint:content` fails on undefined tags.

**7. Images and diagrams.** Copy supplied images to `static/img/posts/<slug>/`, compress with `pngquant --quality 70-90 --ext .png --force`, add alt text and a `*(Figure N: ...)*` caption. Prefer Mermaid code fences for diagrams you create; draw.io SVGs only if the author supplied them.

**8. Code.** Short snippets stay inline. Runnable or multi-file code goes in the code repo `https://github.com/dineshgopal29/the-agentic-advantage` (clone next to this repo as `../the-agentic-advantage` if missing): branch `post/<slug>`, folder `<slug>/` with `README.md`, `requirements.txt`, sources, sample inputs. Run `python -m py_compile` on Python files (never run code that needs secrets; say "not executed" in the PR). Open a PR there. In the post link to `https://github.com/dineshgopal29/the-agentic-advantage/tree/main/<slug>` and note in both PRs that the code PR merges first.

**9. Social assets.** `python3 scripts/publish/social-card.py <file>` (in the worktree). Write `publishing/social/<slug>.md`: a LinkedIn post (80-150 words, a hook line, 3 takeaways, the live URL `https://aisocialjournal.com/<permalink>`, 3-5 hashtags, no emoji spam).

**10. Check.** In the worktree run `npm run lint:content`, `npm run build`, `npm run check:drafts`; fix everything. If you added external links, `npm run check:links` after the build. Re-read the post once against the draft for invented claims.

**11. PR.** Include 3 alternative titles (different angles, each <= 60 chars) so the author can swap one in. Commit on `post/<slug>`, push, `gh pr create --base main` using `pr-template.md` (title `Queue: <post title>`; labels `blog` or `guide`, and `queued`; create labels if missing). Fill "Verify before merge" honestly.

**12. Wrap up.** Move the draft to `drafts/processed/`. Report to the author: PR URL(s), preview command (`cd ../my-journal-posts/<slug> && npm start`, drafts are visible in dev), queue position and projected go-live (`npm run -s queue` after merge, or reason from the cadence), the verify list, and decisions you made that they may want to change. After the author merges, they (or you on request) run `scripts/publish/finish-post.sh <slug>`.

## When things go wrong

- Build fails with a broken link to a queued post: links to other queued posts must not exist until those are released; link only to published content or to the same post's own assets.
- Unknown tag, missing image, duplicate slug: fix at the source, do not weaken the lint.
- Author asks to change the schedule: edit `publish_order`/`publish_on` in the post frontmatter (or `publishing/config.json` for the cadence) via a PR.
